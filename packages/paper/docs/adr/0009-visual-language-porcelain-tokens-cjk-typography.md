# The visual language is "Porcelain, softened" — CSS-variable tokens + evidence-based CJK typography

## Context

As the style evolved, the colors became a mixture: Tailwind grays (#d1d5db / #e5e7eb / #6b7280), GitHub blue (#2563eb), and GitHub syntax colors coexisted without intent, and there was no single source of truth. Under the goal of "the simplest, most eye-restful render," we decided to tidy up the entire visual language. The inspiration started from the [beaket/ui porcelain theme](https://github.com/beaket/ui/blob/main/src/themes/porcelain.css) — _"Industrial precision. Pure white, cold blue-black ink, ghostly shadows."_

During design a core tension surfaced: porcelain is one body of two things — the **discipline of restraint** (no ornament, one pattern, functional shadows) and a **clinical coldness** (pure white, blue-black, hard shadows). Our objective term ("most comfortable") conflicts with the latter. The conclusion: **accept the discipline, but yield the cold aesthetic in exactly one place** — canvas luminance. Pure white #fff is high-luminance and the classic culprit of eye fatigue over long writing sessions, so we keep the cold, clinical feel but use a near-white at lowered luminance.

A separate requirement was raised: the typographic rhythm (margins, line spacing, measure) must be validated not by "self-consistency" but against **multilingual readability standards and research**. We surveyed Korean / Japanese / English primary sources (W3C JLREQ and KLREQ, WCAG 1.4.12, KRDS, and direct measurements of real high-readability products) and cross-checked our values.

## Decision 1 — Color: porcelain palette, `:root` CSS variables as the single source

All colors are defined as `:root` CSS variables in `index.css`, and `theme.ts` and each extension reference them with `var(--x)`. This is possible because CM6's `EditorView.theme` accepts a `var()` string verbatim as a value. Dark mode is out of scope this round, but thanks to the token structure it can later be added with a single `@media (prefers-color-scheme: dark)` block (the X-ray values porcelain already defines) — no JS required.

> **Rendering hygiene (2026-06-15):** the `body` gets `-webkit-font-smoothing: antialiased` + `-moz-osx-font-smoothing: grayscale` (inherited by the editor). The macOS subpixel (auto) default makes edges slightly heavy and uneven, so we standardize on grayscale-AA, the de-facto standard for polished Mac sites. On Retina (dpr2) the difference is minute, with zero loss. Also, the browser-default `body` `font-family` is a serif (`Times`), which was a latent bug leaking serif into shell/menu text outside CM — we block it by pinning a sans stack.

> **Surface-contrast trap (found via validation):** at first the panels used `frost (#f3f4f6)`, but once the canvas was lowered from #fff to #f7f8fa, frost-vs-canvas dropped to 1.04:1 (ΔL 3.4%) and was **effectively invisible** (a borderless code block became indistinguishable from body text). So we derived a panel-only `--surface (#eceef2)`. Surfaces that have a border (table grid, inline chips, overlays) were barely affected since the border carries the separation; the direct hit was **code blocks, which were separated by background alone**. The lesson: on a near-white canvas, a "faint gray panel" must explicitly secure a ΔL against the canvas.

## Decision 2 — Form: zero chrome · global radius 0 · hard-offset overlays

- **Zero chrome**: the whole window is a single `--canvas` plane, with a centered 680px writing surface and a top breathing space (currently 40px — revised 2026-06-15, see below). No title bar, toolbar, or status bar. This matches CONTEXT.md "lightness / visual minimalism" exactly. The markdown copy corner icon (the only always-on UI exception, from ADR-0007) is not removed but **only restyled**.
- **Global radius 0**: follows the porcelain "no radius" discipline. Inline code chips, table cells, toolbar buttons, and overlays all have square corners. (The `radius` that ADR-0006 gave the `.cm-inline-code` decoration is removed.)
- **Overlays = porcelain hard offset**: the slash menu, toasts, and the table floating toolbar use a `2px 2px 0 0 chrome` offset + 1px silver border instead of a blur shadow. The body abandoned brutalism, but the manipulation UI reveals the porcelain DNA.
- **Tables (the core differentiator)**: a precise grid — silver 1px full border, surface header with weight 600, active cell with a signal-blue inset ring.
- **Table spacing and handles (revised 2026-06-14)**: the table-widget padding is set to 0 — table spacing is **symmetric**, coming solely from the blank lines above/below (block rhythm). (Previously `4px 18px 18px 0` permanently reserved space for the hover handle, making the bottom ~14px wider than the top.) The add-column (`add-col`) handle overlaps the table's right edge, and the add-row (`add-row`) handle is a **hover overlay** on the blank line below. Pushing the handles outside the table (into the shell margin) would cause horizontal overflow → a scrollbar, so add-col is left overlapping the right edge.
- **Horizontal rule (revised 2026-06-14)**: `---` / `***` render on cursor-less lines as a **silver 1px full-width horizontal rule** (within one blank-line row height, radius 0). Move the cursor onto it and the `---` text is exposed for editing — the same rule as tables and code fences: "structural syntax is visible only on the active line." Previously it remained as gray `---` glyphs, the one block that was never visualized.
- **Code block top/bottom padding (revised 2026-06-14)**: when outside the cursor, the opening/closing fence lines (the triple-backtick lines) are shrunk into a **~0.5em-tall empty surface strip** to serve as intentional padding (`font-size:0.5em; line-height:1` — a widgetBuffer remains on the empty line, so line-height alone won't flatten it to a single line). Previously the fences remained as full-height empty code lines, an accidental ~1.6em gap. This realizes Decision 3's "0.5em perimeter" intent on the vertical axis in practice.
- **List hanging indent (revised 2026-06-14)**: list item lines get `padding-left + negative text-indent` (proportional to the content start column, in `ch` units) so that a **wrapped second line aligns to the content start, not the marker**. It is applied regardless of cursor presence to prevent a horizontal jump on entry. Because the font is proportional, the `ch` approximation indents nested items slightly more, but with no readability impact.
- **Shell padding reduction (revised 2026-06-15)**: `.editor-shell` padding `64px 24px` → `40px 20px`. The top breathing space was excessively wide, so little body text fit on the first screen. The 680px writing surface (measure, Decision 3) is unchanged — most of the left/right "margin" is the result of the `max-width:680px` centering, not padding, so reducing only the padding leaves the measure invariant.
- **Markdown copy icon background (revised 2026-06-15)**: the corner icon's default background is changed from transparent to opaque `--canvas`, and its dimming is changed from element `opacity:0.55` to the text color (`--muted`) alone. The cause: when first-line text reached the top-right of the writing surface, the glyphs showed through behind the icon and mixed in — **element `opacity` makes even the background semi-transparent**, so the glyphs bled through even with a `--canvas` background laid down. Expressing the dimming with color only lets us keep an opaque background (being the same color as the canvas, it melts in seamlessly on an empty plane). The corner affordance takes visual priority over body glyphs.
- **Heading hierarchy (a restrained ramp)**: h1 1.5 / h2 1.3 / h3 1.15 (650) / h4–6 1em 700. It whispers through size and weight only (margins are no longer used for hierarchy — Decision 4).

## Decision 3 — Typography: system fonts first + a rhythm validated by evidence

**Fonts = system-first, zero web fonts.** Latin uses SF Pro/Segoe; CJK uses natives like Apple SD Gothic Neo. This satisfies both CONTEXT.md "lightness" (CJK web fonts are several MB) and "CJK first-class" (natives are best per platform). The differentiation comes not from the Latin font but from the CJK handling and rhythm. (Unified web fonts like Pretendard were rejected — weight.)

**Japanese body = ヒラギノ角ゴシック (the standard).** The pinnacle of the macOS system Japanese fonts and the default for body text. Rounded gothic (丸ゴ) and mincho (明朝) are casual/literary _styles_ and not the body-text standard, so they were rejected. The Windows fallback is `BIZ UDPGothic` (a Morisawa UD design targeting legibility) → `Meiryo` in order. **游ゴシック (Yu Gothic) is avoided for body text** — it has a chronic problem of glyphs becoming かすれ (faint) on Win Chrome and non-HiDPI (a consensus among Japanese practitioners), and Noto Sans JP, being a web font (several MB), violates the lightness principle. (2026-06-15)

> **The font-interception trap in a mixed CJK stack — the biggest discovery of this session (2026-06-15, confirmed by measurement):** if the stack is ordered `…Apple SD Gothic Neo, Noto Sans KR, Hiragino…`, then **Japanese is drawn in the Korean font, not in Hiragino.** This is because `Apple SD Gothic Neo` (Korean) contains kana and kanji glyphs and comes earlier in the stack — CSS font-family uses, per character, "the first font that has a glyph," so Japanese kana get caught at the Korean font's turn first. The result: the kana letterforms and 約物 (punctuation) spacing differed subtly from zenn/note (all Hiragino) and looked "awkward/cheap." **Measured evidence**: the width of a Japanese string in our stack matched `Apple SD Gothic Neo` exactly to the pixel (and did not match Hiragino). **Fix**: place the Japanese fonts (Hiragino, BIZ UDPGothic, Meiryo) **before** the Korean fonts. Hangul is absent from Japanese fonts, so it automatically falls back to `Apple SD Gothic Neo` and is preserved (re-measured and confirmed). **Accepted trade-off**: shared Korean/Japanese Han characters (漢字, Unicode-unified) now unify to the Japanese letterforms — pure-Hangul documents are unaffected, and modern Korean exposure to Han characters is rare, so it is accepted. We record the intrinsic limitation that CSS alone cannot branch the Han letterforms by language in a mixed document (neither a lang tag nor `unicode-range` can separate unified Han).

**The rhythm was validated against Korean / Japanese / English primary sources.** We confirmed that our CJK-first intuition largely agrees with the standards, and corrected two things (making letter-spacing explicit, and separating the space above headings).

## Decision 4 — Vertical rhythm: one blank line is the sole spacing unit (revised 2026-06-14)

Measuring the full syntax sample, **two units** coexisted in the vertical spacing: (1) the **one rendered row = 1.75em (29.75px)** that a markdown blank line becomes, and (2) a heading-only **margin-top 1.2em (20.4px)**. When a heading had a blank line before it, the two added up to ~50px; with consecutive headings (no blank line), it was 20px — **two different beats for the same heading element**. That was the identity of the "lack of unity."

**Decision: abolish the heading-only margin-top.** One blank line (1.75em) becomes the sole vertical spacing unit for every block — a heading follows the same rule as paragraphs, lists, and quotes. This yields **"one rule, one size"** — the second beat (1.2em) disappears.

- This is **not** "deterministic spacing" or a "baseline grid." Spacing is still a function of the number of blank lines the author typed (heading with a blank line 1.75em / without 0). That is correct under the **markdown = the sole truth** principle. What we removed is the _heading-as-spacing-special-case_ and the _second-size beat_, not author control.
- **For standard authoring (blank line before a heading, body right after) it actually improves**: above a heading drops from 50→29.75px, and below stays 0px → the asymmetry that groups a heading with the body that follows is preserved.
- A heading line renders at 31~35px because of its font size, so it does not land exactly on the 29.75px grid. Since we make no grid claim, this is not a problem.

**Accepted regression: consecutive headings (h_n stuck together without a blank line) collapse from 20px to 0px and touch.** Size and weight differences still distinguish them, but it is tight. In real use, writing headings back-to-back without a blank line is rare, and a blank line can be added when needed (author control = consistent rule). We confirmed readability in browser validation and accepted it.

### Re-revision 2026-06-15 — heading asymmetric margins restored (Zenn measurement basis)

This overturns the "single beat" decision above. **Live measuring the Zenn body** the user took as a reference, headings carry strong asymmetric margins (h2 above 2.3em · below 0.79em, h3 above 2.25em · below 0.50em — not a uniform blank line). This is the de-facto standard of the Japanese dev community (note, Qiita, etc.). After rendering the A/B directly in the editor for comparison, we adopted the asymmetric-margin side (section starts are crisper).

- **Implementation**: `blockSyntaxHiding` attaches `.cm-heading-line .cm-h{1..6}` line decorations to heading lines **regardless of cursor presence** (preventing a jump on entry — the same principle as the list hanging indent), giving per-level `padding-top` (h1 1.6em / h2 1.4em / h3 1.1em / h4–6 0.9em) and a `padding-bottom` of 0.1em.
- **padding, not margin**: CM6's height model cannot measure a `.cm-line`'s margin, so cursor coordinates accumulate error (drift). padding is included in the line box, so `lineBlockAt` ↔ DOM agree (drift = 0, `posAtCoords` accurate). Verified.
- **Specificity**: this has the same specificity as baseTheme's `.cm-line { padding: 0 }`, so it conflicts — we raise the selector to two classes (`.cm-heading-line.cm-h2`) to win.
- **Adding to the blank line**: in standard authoring (a blank line before the heading), above = blank line (~30px) + padding → h2 ≈ 54px, below = padding 0.1em + (if any) blank line. The "two beats" concern remains, but a heading almost always comes with a blank line, and consecutive headings **actually improve** (0px → padding). Author control (the blank line) is preserved.

#### Re-revision 2026-06-16 — h2 space above 1.4em → 0.4em (compactness first)

The user requested reducing the space above H2 for first-screen density. For a heading that comes right after body text with no blank line (the authoring style of this session's sample document), 1.4em floated too far above. **We lower h2 only, to 0.4em** (h1 1.6em / h3 1.1em / h4–6 0.9em retained — the request was scoped to H2, and h1 occurs once at the top of the document so its impact is small). The asymmetry (above > below) principle itself is preserved; only its strength is reduced. To revert, restore `blockSyntaxHiding`'s `.cm-heading-line.cm-h2` paddingTop to 1.4em.

## Decision 5 — Blockquotes: specificity-trap fix + nesting-depth visualization (2026-06-15)

**(1) Dead padding (a regression).** `blockSyntaxHiding` gave quote lines `.cm-blockquote-line { padding-left: 0.7em }` and code lines `.cm-codeblock-line { padding: 0 0.78em }`, but these have the **same specificity (0,0,1,0)** as baseTheme's `.cm-line { padding: 0 }`, so they lost by source order → measured `padding-left: 0px`. Quote text was glued to the vertical bar, and code to the surface edge. Decision 4's heading margins had already dodged this trap by using two classes (`.cm-heading-line.cm-h2`), but quotes and code, being one class, were caught. **Fix**: raise the selectors to `.cm-line.cm-blockquote-line` and `.cm-line.cm-codeblock-line` (0,0,2,0) to win.

→ **Rule (invariant)**: every block-line decoration that gives padding to `.cm-line` must raise its selector to two classes. With one class it loses to baseTheme and silently becomes 0 (revealed only in the browser — jsdom cannot interpret compound-selector specificity, so a regression test cannot catch it).

**(2) Nested-quote visualization.** Previously a single `.cm-line` merely had the `.cm-blockquote-line` class twice, giving a single border → nesting (`> >`) was **visually identical** to one level (a case the sample left for inspection). **Decision**: count the number of Blockquote nodes wrapping each line = the nesting depth, attach a `cm-bq-d{1..4}` class (clamped at 4), and at depth d, indent the text by `d × 1.1em` and draw vertical bars (2px `--chrome`) at positions `k=0..d-1` (the GitHub/Obsidian convention). The outer bars continue from the parent line, and the inner bars remain short, only within the nested span.

- **The bars are not `border-left` but multi-layered `background-image`** (`linear-gradient` × d, positioned at `k×1.1em`). Several bars must be drawn at arbitrary x within a single line, which a single border cannot do. background does not participate in layout → only `padding-left` enters the line height, keeping CM6 coordinates safe (the same margin/padding logic as Decision 4).
- Depth is computed regardless of cursor presence → no horizontal jump when entering edit (the same principle as the list hanging indent and heading margins). The line with the cursor exposes the `> >` marks for editing while keeping the bars and indent.

## Decision 6 — Quote key behavior: Enter (escape) + Tab/Shift+Tab (level inc/dec) (2026-06-15)

We define the nested-quote key behavior (`blockquoteKeymap`). **The Obsidian approach** — Enter focuses on escaping, and level inc/dec is split off onto Tab-family keys. A single key (Enter) cannot do both "fast escape" and "up one level" at once (the former is per-level, so escape is slow; the latter is a fast escape, so it lacks per-level). Standard comparison: Obsidian = Enter escapes entirely + level via Tab/command; lang-markdown default = Enter per-level (auto separator line, slow); rich editors (Notion etc.) = tree-node lift (requires a separate model → impossible, conflicting with the markdown = sole truth principle). We chose the Obsidian approach, which is text-based and matches the user's "fast escape" taste.

- **A line with content**: continue at the same depth (`> > foo` then Enter → next line `> > `). If the cursor is mid-line, split at the same depth.
- **An empty quote line**: **escape the quote entirely** — remove all `>` regardless of depth. The marker line is changed to a blank line (`\n`), **leaving an empty separator line, with the cursor on a new line below it**. Depths 2 and 3 escape with `content then Enter twice`, exactly like depth 1 (the Obsidian/CommonMark standard).
  - **Why an empty separator line is mandatory (a measured bug)**: if you erase only the marker to make a blank line and type immediately in its place, text stuck directly below the quote with no blank line gets absorbed back into the quote paragraph above via **CommonMark lazy continuation** and re-renders inside the quote (at the same depth). Measured: after escaping `> >> adf` (depth 3) and typing `qwer`, the `qwer` line got `cm-blockquote-line cm-bq-d3` and showed as nested. A single separator line definitively ends the quote and blocks the absorption. As a bonus, the cursor moves down a line, also resolving "I pressed Enter but it didn't move."
- **Tab / Shift+Tab (on a quote line, both empty and content lines)**: inc/dec the current quote line's level (the same location as Obsidian's quote-level inc/dec = the current line). Tab = one level deeper (`> > ` → `> > > `, `> > x` → `> > > x`; the markers increase so it is always safe as a new nesting, no separator line needed). Shift+Tab = one level shallower:
  - **Empty line**: since you are about to type there, **a separator line is auto-inserted**. For depth d→d-1, insert `[a depth d-1 empty quote line (separator)] + [a depth d-1 line]` so the typed text is not absorbed by the deeper paragraph above via lazy continuation (measured: `> > inner` / `>` / `> one-up` → `cm-bq-d1`). At depth 1, escape (same as the Enter escape).
  - **Content line**: reduce only the prefix by one level (`> > x` → `> x`, and at depth 1 `> x` → `x` plain text). An independent line renders as intended (measured: `> > content` → `> content` → `cm-bq-d1`). _Limitation_: pulling just one middle line out of a deep multi-line paragraph may absorb it into the line above via lazy continuation, but it is a rare case with ambiguous meaning, so it is accepted.
  - On a non-quote line it returns false → preserving the default Tab (focus move) and the cell sub-view Tab. (Initially it only worked on empty lines, but feedback was that pressing Tab on a content line only flung focus out of the editor — "the expected behavior doesn't happen" — so after measuring we extended it to content lines.)
- Depth and prefix are parsed directly from the line text's `>` prefix (markdown = sole truth, no separate model). But **guard with syntaxTree on whether it is really inside a Blockquote node** — so a line like `> shell prompt` inside a code block is not mistaken for a quote.

**Revision (same day): we first implemented "outdent one level at a time" (chosen by the user in AskUserQuestion) but discarded it in real use.** Because an empty quote line's outdent stayed in place (no line break), escaping from depth 2 required Enter 3 times, and at each intermediate step **the cursor stayed trapped on the same line and would not move down**, producing the unnaturalness of "I pressed Enter but it didn't move + when I type I'm still inside the quote" (measured in the browser, plus user feedback). The abstract choice picked via preview **was overturned by the live behavior** — re-decided as a full escape (unified with depth 1's natural behavior). Korean composition is also fine immediately after escape (the composition guard intact, ADR-0004) — confirmed.

- **List/task lines inside a quote (`> - a` · `> 1. a` · `> - [ ] a`) are yielded to markdownKeymap.** We handle only the `> ` prefix and would drop the list marker, so we let the library join the quote + list markers on that line (our handler owns only plain quote lines in a Blockquote). It also yields if the cursor is mid-prefix (to avoid splitting the marker).

**Trap (recorded): lang-markdown's `markdown()` auto-registers `markdownKeymap` at `Prec.high`** (`addKeymap` defaults to true, internally `support.push(Prec.high(keymap.of(markdownKeymap)))`). This intercepts Enter with `insertNewlineContinueMarkup` (quote/list continuation), and that was the identity of the old behavior where you **could never escape a quote** because even an empty quote line kept continuing. If we place our handler at the same `Prec.high`, registration order makes `markdownExtension()` first, so it is **shadowed** (measured in browser: handler not called). So `blockquoteKeymap` is placed above it at `Prec.highest`, but it yields to the slash menu (`slashCommand`, which uses Enter/Tab and is also highest) by registering **after** it in `createEditor` (at the same precedence, the earlier registration wins). The remaining Enters (list continuation etc.) are still handled by `markdownKeymap` (we return true only inside a Blockquote). The table's Tab is cell-sub-view-only and unrelated to the main view.

- No intervention during IME composition (`view.composing` guard, ADR-0004) — same as codeBlockEnter.
- Validation: in addition to direct-call tests (depth 1/2/3 continuation, full escape, split, code guard, list yield, Tab/Shift+Tab inc/dec), an **integration test that fires real keydowns at the keymap** deterministically confirmed precedence over `markdownKeymap`, "Enter twice → type," **Korean composition**, and the **lazy-continuation regression** (the line typed after an escape/Shift+Tab renders with the intended depth class) — identical results in jsdom and the live browser. Automation tools' synthetic physical keys deliver keydown unreliably, so we take the keymap integration test as the real evidence.

## Conscious acceptances / rejections

- **h4–h6 are nearly indistinguishable from bold body text** — being 1em·700 and separated only by the space above, they resemble strong (700). It is a real, on-screen-confirmed defect, but deep headings are rare in real use and h1–h3 carry the hierarchy, so it is **accepted**. The alternatives (color demotion, a label tier with letter-spacing + smallcaps) were rejected for the sake of simplicity.
- **Pure-white #fff canvas rejected** — minimizing eye fatigue takes priority over porcelain fidelity. The coldness is kept and only the luminance is yielded (#f7f8fa).
- **Dark mode out of scope this round** — only the tokens are prepared. When needed, add a single `@media` block using the porcelain X-ray values.
- **A cold re-coloring of the syntax rejected** — keep GitHub Light's proven readability (inherited from ADR-0006). Only the code surface (background/border) becomes a porcelain neutral.

## Implementation notes (CJK first-class / testing)

Pure color/theme edits are low IME risk, but if you touch the internals of `tableWidget.ts`, `inlineSyntaxHiding.ts`, `blockSyntaxHiding.ts`, or `listRendering.ts`, keep the `imeComposition` / `composingGuard` tests (the ADR-0004 contract) green and validate in Chrome one step at a time per the CLAUDE.md rule.

## Amendment (2026-06-21) — dark mode shipped, Paper rename, the porcelain token bridge

The body above is historical (the prototype state). Three things have changed in the production package (`@beaket/paper`) since:

1. **Dark mode shipped (v0.2.0).** The body says dark mode is "out of scope this round" with only the tokens prepared. That is now stale — dark mode is implemented and released. `src/editor/theme.ts` carries a full `darkTokens` map (dark-aware ink `#e6eaee`, canvas `#14171c`, surface `#1c1f27`, the inverted neutral ramp, dark accent `#1a8ed8`, and a GitHub-Dark-Default syntax ramp), plus a public `ColorScheme` type (`"light" | "dark" | "system"`) and `darkThemeStyle()` / `setColorScheme()` / `colorSchemeClass()`. The architecture matches the body's prediction: dark is delivered as a scoped `@media (prefers-color-scheme: dark)` stylesheet (plus an unconditional forced-dark block), so each token keeps its `var()` chain and only the built-in fallback default swaps. Note: dark mode is implemented as a separate injected stylesheet rather than a single `EditorView.theme` `@media` block — CodeMirror's style-mod maps the root to `&`, but a nested `&` inside `@media` emits invalid CSS the browser discards, so the dark token block ships via `darkThemeStyle()`.

2. **`BeaketPaper` → `Paper` (PR #455, v0.3.0).** The React component and its handle/props are now exported as `Paper` / `PaperHandle` / `PaperProps` from `@beaket/paper/react`.

3. **The token contract is the porcelain bridge in code now.** The body describes `:root` CSS variables and a future porcelain dark block. In the shipped package the tokens live on the `.cm-editor` scope (so the package is self-sufficient, depending on no consumer `:root`), and each token resolves through a deliberate fallback chain: `var(--beaket-paper-X, var(--color-Y, default))` — ① the public `--beaket-paper-*` consumer override, ② the **porcelain** `--color-*` bridge (matching for free, and inheriting porcelain's dark block, when rendered inside `@beaket/ui`'s porcelain theme), ③ the built-in default. This token-reconciliation work is recorded in ADR-0013 (decision 6). The two documented local divergences from porcelain still hold and match the body's measured values exactly: `--color-ink` is pinned softer at **`#232a35`** (porcelain's `#0a0d14` is too harsh on the near-white canvas), and `--canvas` is the editor-owned **`#fbfcfd`** (not porcelain's `--color-paper` #fff). The CJK font-stack ordering (Hiragino/BIZ UDPGothic/Meiryo **before** Apple SD Gothic Neo/Noto Sans KR), the `--font-size: 17px`, `--line-height: 1.75`, and the opt-in `--measure` token are all present and unchanged, and `letter-spacing` is intentionally still not exposed as a token (negative spacing breaks mixed CJK). The font-ordering invariant is pinned by `theme.test.ts`.
